# システム全体像 — 収集から Instagram 公開まで（2026-08-19）

別サイトへの横展開を想定して、**1物件が公開されるまでに何がどこで起きるか**を
上から順に書く。運用ルールの根拠は各 docs/ の個別文書にある。

## 一行でいうと

```
収集 → 採点(LLM) → 審査(人) → 納品(Drive) → 投稿予定 → 本文生成 → 投稿(API)
                                                          → ストーリーズ(手動)
                                                          → 週次リール(自動)
```

**人が判断するのは審査の1箇所だけ。** それ以外は全部自動で、
どの工程も特定のPCに依存しない。

## 構成要素（どこで何が動くか）

| 場所 | 役割 | 動くもの |
| --- | --- | --- |
| GitHub Actions | 定期実行の本体 | 収集・採点（毎朝9時）/ 納品（日中1時間おき）/ 週次リール（月曜19時）/ 手動メンテナンス |
| Render | 審査UIと投稿 | FastAPI の Web アプリ。人の審査、投稿予定の閲覧、**投稿ワーカー**、**Meta へ画像を配る口**（/m/トークン） |
| Neon (PostgreSQL) | 唯一の状態置き場 | 物件・スコア・審査結果・納品記録・投稿予定・IGトークン・投稿画像の実体 |
| Google Drive | 納品先 | 共有ドライブ。認証は Workload Identity（鍵レス） |
| Meta (Instagram API) | 公開先 | graph.instagram.com。Instagram ログイン方式 |

状態はすべて Neon に置く。Actions・Render・手元の Mac は同じDBを見るので、
どこで実行しても同じ結果になる（Render のディスクは揮発するため、
投稿画像もファイルではなくDBの行で持つ）。

## 手順 — 1物件の一生

### 1. 収集（GitHub Actions・毎朝9時）

- 設定済みソース（config.yaml の editorial_sources）を巡回。**公式RSSを優先**し、
  足りないソースだけ一覧ページを見る
- 守る線: robots.txt 尊重（fail-closed）/ 同一ドメイン3秒間隔・並列なし /
  User-Agent に連絡先 / ログイン・CAPTCHA・bot検知の回避はしない
- `source_url` に UNIQUE 制約。**何度回しても同じ記事は二度入らない**

### 2. 採点（同じ実行の中）

- LLM（Haiku）が記事を読み、承認基準（config.yaml の scoring）に沿って
  スコアと理由を付ける
- 同時に**投稿の材料を抽出**する: 物件名（display_name）/ 説明文
  （caption_body・日本語3〜6文）/ Location・Usage・Architect・面積・築年 /
  様式 / 州・地域 / 写真クレジット。**記事に書かれた事実だけ**。
  無い項目は空のまま（後段は空の行を出さない）
- 併走する「学習」: 人が書いた非承認理由を分類し、繰り返された指摘を
  ルール候補にする。**候補止まり**で、プロンプトに載るのは審査UIで
  人が承認したものだけ

### 3. 審査（人・審査UI）

- Render の審査UIで承認/非承認。ここが**唯一の人の判断点**
- 非承認には理由を書く（それが2の学習の入力になる）

### 4. 納品（GitHub Actions・日中1時間おき）

- 承認済みで未納品のものを拾い、画像を加工して Drive の共有ドライブへ
  フォルダ納品（frmg_igNNN 連番 + meta.txt）
- 認証は **Workload Identity**（GitHub の OIDC を Google が検証。鍵ファイルなし）
- 納品の前に**疎通確認**が走り、権限が足りなければ1件も書かずに止まる
- `deliveries` 記録で冪等。**再実行しても二重納品しない**

### 5. 投稿予定の作成（GitHub Actions・毎朝、収集の最後）

- `post plan` が3日先まで予定を並べる。**対象は納品済みだけ**
  （納品まで通った＝画像がある、という保証を使う）
- スコアの高い順。**在庫が足りない日は枠を空ける**（基準を下げて埋めない）
- 週1でリールの枠も1つ置く
- 予定は審査UI（/schedule）に出るので、**人が朝いちで見て止められる**

### 6. 本文生成（予定を作った時点）

- 実運用の投稿4本から起こした型に、2で抽出した材料を流し込む:

  ```
  リード（日英2行・固定）
  【 物件名 】
  仕様欄（値のある行だけ）
  説明文（日本語）
  Photo: 撮影者（取れた場合）
  CTA 3行 / 締め2行 / 事業案内 / 英文の注記（固定）
  ハッシュタグ1行（ブランド→物件名・設計者→様式→地域→汎用）
  ```

- **価格は載せない。値の無い行は出さない。** 型を変えたら
  `post replan` で未投稿分だけ作り直せる

### 7. 投稿（Render の投稿ワーカー・予定時刻）

- `auto_post: true` のとき、ワーカーが1分おきに「時刻が来た予定」を見る
- 取得と状態変更を1文のSQLで行う（planned → publishing）。
  **2つのワーカーが同じ予定を拾えない**＝二重投稿の防止
- 手順: 画像をDBから配信用トークン付きURLに載せる →
  Meta にコンテナ作成（**Meta がこのURLへ画像を取りに来る**）→
  仕上がり（FINISHED）を1分おきに最大5分待つ → 公開 → permalink を保存
- 失敗は3回まで自動リトライ。1日100件のAPI上限は仕組み上届かない
- IGトークンは60日で失効するため、**毎朝の定期実行が自動更新**する

### 8. ストーリーズ（人・毎日1回）

- **自動化しない。** APIのストーリーズは「投稿をストーリーズに追加」の
  リンク付きの形にできず、キャプションもスタンプも載らないため
- Business Suite / Instagram アプリから、その日の公開投稿を
  「投稿をストーリーズに追加」で共有する（1日1投稿なら1件・1分）

### 9. 週次リール（GitHub Actions・月曜19時）

- 直近7日の投稿からリーチ上位7枚を選び（要 insights 権限）、
  ffmpeg で 1080×1920 の動画に組む（背景ぼかし＋ゆっくり寄る）
- 音源はライセンス確認済みの同梱マスターをローテーション
  （CC BY はクレジットを本文に必ず入れる）
- 動画は rupload.facebook.com へ**直接アップロード**するので公開URLが不要。
  だから画像を配れない Actions からでも投稿できる

## 状態遷移（つまずいたらここを見る）

```
物件:  collected → scored → (approved | rejected) → delivered
投稿:  planned → publishing → published
                └ failed（3回まで戻る）/ skipped（人が見送り）
```

## 横展開チェックリスト — 別サイトで同じものを動かすには

このシステムは**1ブランド1セット**の作り。展開先ごとに次を用意する。

### 複製するもの（外部サービス4つ＋リポジトリ）

1. リポジトリ（このリポジトリを流用。config.yaml がブランドの実体）
2. Neon のDB（新しいデータベース1つ）
3. Render のWebサービス1つ（審査UI・無料プランで可）
4. Google 共有ドライブ（納品先。既存ドライブの別フォルダでも可）
5. Instagram プロアカウント ＋ Meta アプリ（アプリは使い回しも可。
   トークンはアカウントごとに1本で、DBに置くので混ざらない）

### 書き換える設定（config.yaml）

- `editorial_sources` — 収集先。**必ず robots.txt と写真の権利を確認してから**
  有効化する（フィードが読めることと写真を使ってよいことは別問題）
- `caption` — 投稿の型・文言・タグ・事業案内
- `instagram` — app_id / public_base_url（RenderのURL）/ post_times / 枠数
- `scoring` — 承認基準（そのブランドの目利き）
- `drive` — 納品先フォルダID・共有ドライブID

### GitHub Secrets（5つ）

| 名前 | 中身 |
| --- | --- |
| DATABASE_URL | Neon の接続文字列 |
| ANTHROPIC_API_KEY | 採点用 |
| GCP_WORKLOAD_IDENTITY_PROVIDER | セットアップスクリプトの出力（鍵ではない） |
| GCP_SERVICE_ACCOUNT | 同上 |
| INSTAGRAM_APP_SECRET | 再認可をActionsから行う場合のみ |

### 1回だけの手作業（初回セットアップ）

1. `bash scripts/setup-workload-identity.sh`（Google Cloud 側・約5分）
2. 共有ドライブにサービスアカウントを**コンテンツ管理者**で追加
3. GitHub Secrets 登録
4. IG 認可: `instagram auth-url` のURLをアカウント管理者に送る →
   受け取った code を `instagram exchange-code` で60日トークンに交換
   （スコープは投稿＋インサイト。以後は毎朝自動更新）
5. Render に環境変数 DATABASE_URL と Basic 認証を設定してデプロイ
6. 最初の1本は必ず `post run --dry-run --limit 1` → `--limit 1` で
  実物を確認してから `auto_post: true`

### 運用の決まり（複数サイトでも変わらない）

- **auto_post を true にするのは1ブランドにつき1箇所だけ**（Render）
- 納品ワーカーも1箇所だけ（Actions）
- 収集ポリシー（robots・3秒・回避なし）は全ブランド共通の下限
- Zillow / Redfin / Compass は自動収集しない（手動URL投入のみ）
